# Virtual keys

An `auth:` block turns on downstream authentication: the proxy verifies every
inbound request carries a known credential before it reaches a provider.
Omit `auth:` entirely and today's behavior is unchanged — no
application-level authentication
(`schema/llmproxy-v0.schema.json`'s `auth` field description).

The credential is a **virtual key**: an opaque, proxy-issued bearer token,
distinct from any provider's own API key. A virtual key identifies a caller
to llm-proxy; the provider credential a request is forwarded with is a
separate value attached to the cluster — see
[Providers and clusters](../providers-and-routing/providers-and-clusters/).

## Authentication fails closed; authorization defaults open

These are two different questions, and the code answers them differently on
purpose:

- **Authentication** — "who is this?" — fails closed. With `auth:` present,
  a request carrying no recognized credential is refused with a 401, never
  admitted anonymously.
- **Authorization** — "what may they do?" — defaults open. A tenant with no
  configured policy may use every model and every provider. Restriction is
  opt-in.

This second point matters for what to expect today. `TenantPolicy` carries a
per-tenant model allow-list and spend ceiling, not empty placeholder fields
(`crates/proxy-filters/src/auth.rs:226-251`, the `model_access` and `budget`
fields). Both default open: an unconfigured tenant may use every model and
has no spend ceiling (`crates/proxy-filters/src/model_authz.rs:106-108`,
`ModelAccess::default`; `crates/proxy-filters/src/auth.rs:233-249`, the
`budget` field's doc on why `None` means unlimited). Two more Lane-H filters
enforce these policies, `llmproxy.model_authz` and `llmproxy.spend_limit`
(`crates/proxy-filters/src/model_authz_filter.rs`,
`crates/proxy-filters/src/spend_limit_filter.rs`), and an operator sets a
tenant's allow-list or budget through the admin write API — see "Managing
keys and tenants at runtime" below. None of this reaches the `auth:` block
itself: `schema/llmproxy-v0.schema.json`'s `Auth` type has no allow-list or
budget field, so the `llmproxy` dialect cannot pre-configure either from the
config file. An `auth:` block alone still answers only "who", never "what
may they do".

## What a virtual key looks like, and how it verifies

A virtual key is a bearer token with a printable `llmp_` prefix, generated by
`llm-proxy --mode keygen` (see
[Managing secrets](../authentication/managing-secrets/)) as `llmp_` followed
by 32 random bytes from the OS CSPRNG, base64url-encoded without padding
(`crates/proxy/src/keygen.rs`'s `generate_plaintext_key`,
`KEY_ENTROPY_BYTES`). The client sends it the same way as any bearer token:

```
Authorization: Bearer llmp_<the key>
```

Configuration never holds the plaintext key — only a digest:
`hex(HMAC-SHA256(hmac_secret, <plaintext key>))`, a keyed hash rather than a
plain one, so read access to the configured key set does not by itself let
someone precompute matching keys offline
(`crates/proxy-filters/src/auth.rs`'s module doc, "Why keyed HMAC-SHA256").
Comparison against a presented key is `ring::hmac::verify`, run once against
the single digest that a table lookup already narrowed to — the constant-time
comparison the crate's own module doc explains is `ring`'s documented
replacement for the deprecated
`ring::constant_time::verify_slices_are_equal`
(`crates/proxy-filters/src/auth.rs:493-499`, `KeySet::find`). A
`KeyRecord` — the value stored per digest — carries only `key_id`, `tenant`,
and `revoked`; there is no field for the plaintext key anywhere in the type
(`crates/proxy-filters/src/auth.rs:411-415`).

## An unrecognized credential is not the same failure as a bad one

The authenticator distinguishes two internal outcomes that look similar but
must not be conflated:

- **No credential of this kind** — no `authorization` header, a different
  auth scheme, or a bearer value without the `llmp_` prefix (for example, a
  JWT). This is not a failure of the virtual-key authenticator; it is the
  seam a future OIDC/JWT authenticator (WP-50 increment 2c, not built) is
  meant to occupy.
- **A bad credential of this kind** — an `llmp_`-prefixed value whose digest
  matches no configured key (`UnknownKey`), or matches a key marked
  `revoked` (`RevokedKey`). Both are refused, permanently, for this request.

Collapsing the two would open a probing oracle: a chain of authenticators
that fell through a *bad* virtual key to try a JWT authenticator would leak,
one probe at a time, whether a guessed value was recognized as a virtual key
at all. `AuthenticatorChain::authenticate` stops at the first `Rejected` and
never tries a later authenticator in that case
(`crates/proxy-filters/src/auth.rs:592-621`; the probing-oracle case is
covered directly by
`a_rejected_first_authenticator_short_circuits_a_chain_that_would_otherwise_authenticate`
in `crates/proxy-filters/src/auth_filter.rs`).

## The response on the wire is identical for every failure reason

No credential, an unknown key, and a revoked key all produce the exact same
401: status `401`, body `unauthorized`, and a `www-authenticate: Bearer`
header (RFC 7235 requires the challenge on a 401)
(`crates/proxy-filters/src/auth_filter.rs`'s `AuthFilterInstance::deny`,
proven identical by
`all_three_failure_reasons_produce_an_identical_downstream_response` in the
same file and, end to end over a real socket, by
`all_three_failure_modes_are_byte_identical_on_the_wire` in
`testing/diffrig/tests/auth_e2e.rs`). A caller must not be able to learn from
the response alone whether a key they guessed was ever valid.

The three reasons are recorded separately, but only internally: each call
sets `StreamInfo::response_code_details` to one of `auth_no_credential`,
`auth_unknown_key`, or `auth_revoked_key`
(`crates/proxy-filters/src/auth_filter.rs:357-376`, and
`the_three_failure_reasons_produce_three_different_details_strings` pins the
exact three strings). **This is a real gap, not a documented feature yet:**
`StreamInfo::response_code_details` is populated on every local reply
(`crates/proxy-http/src/filter_manager.rs:1293`, `:1382`, `:2866`), but the
access-log format-string engine has no `%RESPONSE_CODE_DETAILS%` operator —
`crates/proxy-observability/src/access_log.rs`'s operator match has no case
for it, and it does not appear in either the text or JSON access-log format
described in [Access logs](../observability/access-logs/). So today, an
operator cannot yet tell an unknown key from a revoked one by reading the
access log; only the identical 401 is externally visible either way.

## The token limiter keys on the identity the proxy assigned, not the header the caller sent

If a `limits:` entry uses `key: tenant`, the token-rate limiter buckets each
request on `StreamInfo::auth.tenant` — the tenant this filter resolved and
wrote — never on the raw `authorization` header value
(`crates/proxy-filters/src/token_limit_filter.rs:550`, and its module doc's
bucket-key table at lines 103–124). This is a security property, not an
implementation detail: before this filter re-keyed onto the resolved tenant,
it bucketed on a hash of the client-supplied header, so presenting a second,
distinct header value bought a fresh budget — the limit was advisory by
construction. Two virtual keys that belong to the same tenant now draw from
the same budget and cannot be used to reset it, proven end to end by
`two_virtual_keys_on_the_same_tenant_share_one_token_budget` in
`testing/diffrig/tests/auth_e2e.rs`: a second, different key on the same
tenant gets a `429` once the shared budget the first key already spent is
exhausted.

`crates/proxy-config/src/lower.rs`'s `check_lane_h_filter_order` enforces the
ordering this depends on: `llmproxy.auth` must run before
`llmproxy.token_limit` in the filter chain, because decode-path callbacks run
in config order and the limiter reads `auth.tenant` on decode. Reversed, the
limiter would silently fall back to the spoofable header instead — this is a
load-time error, not a warning, naming both filters
(`crates/proxy-config/src/lower.rs`'s `check_lane_h_filter_order`,
lines 1314–1391). The configuration format
never gets this wrong: it always emits `llmproxy.auth` first when an `auth:`
block is present (`crates/proxy-simple-config/src/lower.rs:1506-1513`). A
bootstrap configuration that hand-writes `http_filters` must order the two
itself.

## Configuring `auth:`

```yaml
version: 0
auth:
  hmac_secret: ${LLMPROXY_AUTH_SECRET}
  keys:
    - id: alice-laptop
      tenant: acme
      digest: 3f2a1e9c7b4d5f6a8e0c2b1d4f6a8c0e2b4d6f8a0c2e4b6d8f0a2c4e6b8d0f2a
      revoked: false
providers:
  openai:
    api_key: ${OPENAI_API_KEY}
routes:
  - model: "*"
    provider: openai
```

Exactly one of `hmac_secret` / `hmac_secret_file` is required
(`schema/llmproxy-v0.schema.json`'s `Auth`). See
[Managing secrets](../authentication/managing-secrets/) for generating the
`digest` value and the operational detail of each option.

An empty `keys: []` list is legal — and refuses every request, since nothing
authenticates. It is almost certainly a mistake, so the configuration format
emits a load-time warning rather than silently accepting it
(`schema/llmproxy-v0.schema.json`'s `Auth.keys` description).

## Bootstrap configuration

The engine's underlying filter is `llmproxy.auth`
(`type.llmproxy.dev/llmproxy.filters.v0.Authentication`), the first filter
vendored specifically for this project rather than borrowed from an existing
compiled message (`crates/proxy-api/vendor/llmproxy/filters/v0/auth.proto`).
Its config carries `hmac_secret` (a standard `DataSource`, `filename` or
`inline_string` only) and a `virtual_keys` list of `{key_id, tenant,
digest_hex, revoked}`:

```yaml
http_filters:
  - name: llmproxy.auth
    typed_config:
      "@type": type.llmproxy.dev/llmproxy.filters.v0.Authentication
      hmac_secret:
        inline_string: ${LLMPROXY_AUTH_SECRET}
      virtual_keys:
        - key_id: alice-laptop
          tenant: acme
          digest_hex: 3f2a1e9c7b4d5f6a8e0c2b1d4f6a8c0e2b4d6f8a0c2e4b6d8f0a2c4e6b8d0f2a
          revoked: false
  - name: envoy.filters.http.router
    typed_config:
      "@type": type.googleapis.com/envoy.extensions.filters.http.router.v3.Router
```

Place `llmproxy.auth` before any other Lane-H filter in `http_filters` — see
"The token limiter keys on the identity the proxy assigned" above for why
order is load-bearing, not stylistic.

## Managing keys and tenants at runtime

Minting a key, revoking one, creating or deleting a tenant, and setting a
tenant's model allow-list or spend budget are all bearer-gated HTTP calls
against the admin server, not config-file edits: `POST /keys`,
`DELETE /keys/{id}`, `POST /tenants`, `DELETE /tenants/{id}`,
`PUT /tenants/{id}/policy`, `PUT /tenants/{id}/budget`, and a read-only
`GET /tenants/{id}/spend` (`crates/proxy-admin/src/server.rs:61-79`'s
`AVAILABLE_ENDPOINTS`, and the method table at `:547-555`). Each of these
paths also has a scoped form, `/chains/{stat_prefix}/...`, that names the
target HTTP connection manager by its own `stat_prefix`. Use the scoped
form when more than one chain in this serve configures `llmproxy.auth`:
the unscoped paths are an alias that works only when exactly one chain
does, and refuse rather than guess when more than one does
(`crates/proxy-admin/src/lib.rs:47-63`, and `resolve_control_plane` in
`crates/proxy-admin/src/server.rs`). Each call writes
the store first and republishes immediately, so the change is visible to
every worker's very next request rather than waiting on a periodic refresh
(`crates/proxy-filters/src/control.rs:1713-1775`, `ControlPlane::mint_key`,
`revoke_key`, `set_policy`, `set_budget`, each documented "then republishes").
The write API is fail-closed: with `LLMPROXY_ADMIN_TOKEN` unset, empty, or
whitespace-only, every write returns `403` and a log line naming the endpoint,
never a silent open door (`crates/proxy-admin/src/server.rs:387-395`,
`normalize_admin_token` at `:163-174`). Read endpoints are unaffected by the
token.

Keys and tenant policy live in one of two stores, selected by
`typed_config.store` on the `llmproxy.auth` filter. The default,
`in_memory`, holds everything only for the life of the process. Setting
`typed_config.store.persistent.path` selects `RedbControlPlaneStore`, an
embedded on-disk store that survives a restart of that one process
(`crates/proxy-filters/src/auth_filter.rs:182-213`, `StoreSpec` and
`parse_store`). This selection is Envoy-mode only: the dialect's schema
(`schema/llmproxy-v0.schema.json`) has no `store` field under `auth`, and its
lowering only ever emits `hmac_secret` and `virtual_keys`
(`crates/proxy-simple-config/src/lower.rs:1367-1368`) — a config written in
the `llmproxy` dialect always runs the in-memory store. The admin write API
itself works the same way regardless of dialect, since it talks to whichever
store the chain built.

A `SIGHUP` reload does not change any of this for an already-running
listener. The HMAC secret, the config's bootstrap key list, the store
selection, and the policy-poll interval are all read once, the first time a
worker builds this filter chain, and are reused as-is on every later reload
of that same chain — editing `auth.keys`, `typed_config.store`, or
`poll_interval_seconds` and sending `SIGHUP` has no effect; only a process
restart picks up the new value
(`crates/proxy-filters/src/auth_filter.rs:404-409`, `:455-459`). The admin
write API is the supported way to change keys, allow-lists, and budgets on a
running process; a config reload is not.

## What is not built yet

- **OIDC/JWT authentication.** The seam exists — a JWT-shaped bearer value is
  treated as `NoCredential`, not `Rejected`, specifically so a second
  authenticator can claim it later — but there is no JWT validator today
  (WP-50 increment 2c).
- **A shared, multi-replica store.** `RedisControlPlaneStore` exists and its
  own tests pass against a real Redis
  (`crates/proxy-filters/src/control_redis.rs`), but nothing can select it:
  `StoreSpec` only has `InMemory` and `Persistent` variants, and `parse_store`
  only matches `in_memory` and `persistent`
  (`crates/proxy-filters/src/auth_filter.rs:182-213`). Today every store is
  single-process; running more than one replica means each has its own,
  independent key set and budget.
- **Model allow-lists or budgets from the `llmproxy` dialect's config file.**
  `schema/llmproxy-v0.schema.json`'s `Auth` type has no such field. Setting
  either requires the admin write API or a hand-written Envoy-mode
  `llmproxy.model_authz`/`llmproxy.spend_limit` `typed_config` — see
  "Managing keys and tenants at runtime" above.
