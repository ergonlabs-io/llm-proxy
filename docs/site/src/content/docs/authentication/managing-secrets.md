# Managing secrets

This page is the operational lifecycle of a virtual key: mint one, install
its digest, verify it authenticates, revoke it, and rotate the HMAC secret
that keys every digest. See [Virtual keys](../authentication/virtual-keys/)
for how verification works internally.

**There is no key store and no admin API today.** Every action below is a
config-file edit followed by a `SIGHUP` reload or a restart. WP-50
increment 2b (a persistent/shared `CredentialStore`) and increment 3 (admin
CRUD for keys) are not built — see
[Virtual keys](../authentication/virtual-keys/#what-is-not-built-yet).

## The HMAC secret

Every digest in `auth.keys[]` is `hex(HMAC-SHA256(hmac_secret,
<plaintext key>))`. Set exactly one of:

- `auth.hmac_secret` — an inline value, normally `${LLMPROXY_AUTH_SECRET}`
  interpolated from the environment.
- `auth.hmac_secret_file` — a path, re-read at listener-bind time and again
  on every `SIGHUP` reload, since a reload re-parses the whole config file
  (see [Config reload](../operations/config-reload/)).

Setting both, or neither, is a load error
(`crates/proxy-simple-config/src/lower.rs`'s `lower_auth`: `auth`, "set
either hmac_secret or hmac_secret_file").

**A secret file's trailing newline is trimmed automatically; an inline value
is not.** `echo "s3cret" > secret.txt` — the obvious way to create the file —
appends a newline. Both `llm-proxy --mode keygen --hmac-secret-file` and the
running proxy's own verifier strip trailing whitespace from a *file* before
using it as the HMAC key, so the two agree
(`crates/proxy-filters/src/auth.rs`'s `secret_bytes_from_file`, shared by
`crates/proxy/src/keygen.rs`'s `resolve_secret` and
`crates/proxy-filters/src/auth_filter.rs`'s `parse_hmac_secret`; proven by
`a_secret_file_with_a_trailing_newline_keys_on_the_secret_alone` in
`crates/proxy-filters/src/auth_filter.rs`). An inline `hmac_secret:` value or
`$LLMPROXY_AUTH_SECRET` is used exactly as given — YAML already strips
incidental whitespace around a plain scalar, and a value someone deliberately
quoted with spaces is taken literally.

If you compute a digest by hand instead of with `--mode keygen`, use `printf
%s`, never a here-string — `<<<` appends a newline that changes the digest
(`schema/llmproxy-v0.schema.json`'s `AuthKey.digest` description):

```sh
printf %s "llmp_yourkey" | openssl dgst -sha256 -hmac "$LLMPROXY_AUTH_SECRET" -hex
```

## Step 1: Generate a key

```sh
llm-proxy --mode keygen --tenant acme --key-id alice-laptop --hmac-secret-file secret.txt
```

| Flag | Required | What it does |
|---|---|---|
| `--tenant <TENANT>` | yes | The tenant the generated key authenticates as. |
| `--key-id <ID>` | no (default `REPLACE_ME`) | Names this credential in audit logs and `auth.keys[].id`. |
| `--hmac-secret-file <PATH>` | one of this or `$LLMPROXY_AUTH_SECRET` | Derive the digest from this file's contents; takes precedence over the environment variable if both are set. |

This prints a paste-ready fragment. The values below are illustrative
placeholders, not a real generated key — see
[CLI reference](../reference/cli/#--mode-keygen) for the exact command that
produced a real one:

```text
Key (shown once -- store it now; it cannot be recovered from the config):

  llmp_<REPLACE-WITH-YOUR-GENERATED-KEY>

Add to your llmproxy.yaml:

  auth:
    keys:
      - id: alice-laptop
        tenant: acme
        digest: <REPLACE-WITH-YOUR-GENERATED-DIGEST-64-HEX-CHARS>
```

The plaintext key touches stdout exactly once
(`crates/proxy/src/keygen.rs`'s `run`) — it is never written to a log, and
copy it now: it cannot be recovered from the digest afterward. The key
itself is `llmp_` followed by 32 CSPRNG-generated bytes, base64url-encoded —
256 bits of entropy, the point past which guessing it stops being a
practical attack (`crates/proxy/src/keygen.rs`'s `KEY_ENTROPY_BYTES`).

## Step 2: Install the digest

Add the printed `id` / `tenant` / `digest` block under `auth.keys` in your
configuration file:

```yaml
auth:
  hmac_secret_file: secret.txt
  keys:
    - id: alice-laptop
      tenant: acme
      digest: 3f2a1e9c7b4d5f6a8e0c2b1d4f6a8c0e2b4d6f8a0c2e4b6d8f0a2c4e6b8d0f2a
```

Every field is validated at load time with its dotted path — a duplicate
`id`, a duplicate `digest`, or a digest that isn't exactly 64 lowercase hex
characters is a load error, not a silent accept
(`crates/proxy-simple-config/src/lower.rs`'s `lower_auth`/`validate_digest`).
The bootstrap-configuration equivalent (`llmproxy.auth`'s `virtual_keys`) is
shown in [Virtual keys](../authentication/virtual-keys/#bootstrap-configuration).

## Step 3: Apply it

Restart the proxy, or send it a `SIGHUP` to reload without dropping
connections:

```sh
kill -HUP <pid>
```

See [Config reload](../operations/config-reload/) for what a reload does and
does not pick up. A config that fails to parse or validate — a malformed
digest, for example — leaves the proxy serving the previous snapshot rather
than taking it down.

## Step 4: Verify

```sh
curl -s -i http://127.0.0.1:8080/v1/chat/completions \
  -H "authorization: Bearer llmp_<your key>" \
  -H "content-type: application/json" \
  -d '{"model":"gpt-5","messages":[{"role":"user","content":"hi"}]}'
```

A configured, non-revoked key is forwarded to the provider and returns
whatever the provider returns. Any other case — no `authorization` header,
an unrecognized key, or a revoked one — gets, byte-identically:

```text
HTTP/1.1 401 Unauthorized
www-authenticate: Bearer

unauthorized
```

(`crates/proxy-filters/src/auth_filter.rs`'s `AuthFilterInstance::deny`,
proven identical across all three cases by
`all_three_failure_reasons_produce_an_identical_downstream_response`.) The
identical response is deliberate — see
[Virtual keys](../authentication/virtual-keys/#the-response-on-the-wire-is-identical-for-every-failure-reason)
for why, and for the current gap in telling the three reasons apart
operationally.

## Revoking a key

Set `revoked: true` on the entry rather than deleting it:

```yaml
auth:
  keys:
    - id: alice-laptop
      tenant: acme
      digest: 3f2a1e9c7b4d5f6a8e0c2b1d4f6a8c0e2b4d6f8a0c2e4b6d8f0a2c4e6b8d0f2a
      revoked: true
```

then reload or restart — there is no live revocation without editing
configuration; that is exactly the `CredentialStore` gap noted above. On the
wire a revoked key gets the same 401 as one that was never configured at
all. Keeping the record (instead of deleting it) matters once the access-log
gap described in
[Virtual keys](../authentication/virtual-keys/#the-response-on-the-wire-is-identical-for-every-failure-reason)
closes: `revoked` is the only way the internal `auth_revoked_key` detail
(distinct from `auth_unknown_key`) can ever be produced for that credential.

## Rotating the HMAC secret

**Rotating `hmac_secret` invalidates every configured digest at once** — the
proxy's HMAC input changes, so no existing digest matches any presented key
anymore (`crates/proxy-api/vendor/llmproxy/filters/v0/auth.proto`'s
`hmac_secret` doc: "rotating this secret invalidates every configured digest
at once, so it is a deliberate reconfiguration"). This is why
`hmac_secret_file` deliberately supports no directory-watch mechanism — a
rotation must be a conscious step, not something a file-move event triggers
by accident.

There is no way to carry an existing key across a rotation without the
plaintext: since no component — not the config, not the running proxy —
ever stores a plaintext key (only its digest), recomputing a digest under a
new secret requires the plaintext value, which by design only the caller who
originally received it still has. In practice, treat a secret rotation as
reissuing a key to every caller: generate fresh keys under the new secret
with `--mode keygen`, update `auth.keys` with the new `digest` values,
distribute the new plaintext keys, and reload. Every caller still presenting
a key minted under the old secret gets a 401 the moment the new secret takes
effect.

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| Every request gets `401` / `www-authenticate: Bearer` / body `unauthorized`, even with a key you believe is correct | The digest was computed with a different `hmac_secret` than the one the proxy loaded — often a secret file with (or without) a trailing newline computed one way and consumed another, or `auth.hmac_secret_file` pointing at the wrong file | Recompute the digest against the exact secret the proxy is using; regenerate with `--mode keygen --hmac-secret-file` against that same file |
| Same 401 as above, but the key was working before | The key was set to `revoked: true`, or its entry was removed from `auth.keys` | Check the entry in configuration; both look identical on the wire by design |
| `--mode keygen requires --tenant <TENANT>` | Ran `keygen` without `--tenant` | Add `--tenant <name>` |
| `no HMAC secret: pass --hmac-secret-file <PATH>, or set $LLMPROXY_AUTH_SECRET` | Neither `--hmac-secret-file` nor the environment variable was set | Supply one of the two |
| `--hmac-secret-file <path>: file is empty or contains only whitespace (an empty secret would make every digest effectively unkeyed)` | The secret file exists but has no usable content | Write a real secret to the file |
| Load error naming `auth`: `set either hmac_secret or hmac_secret_file` (or `, not both`) | Configuration set zero, or both, of the two mutually exclusive fields | Set exactly one |
| Load error naming `auth.keys[N].digest`: `must be exactly 64 hex characters` / `must be lowercase hex` | A hand-typed or truncated digest | Regenerate with `--mode keygen`, or recheck the `openssl` command used `printf %s`, not `<<<` |
