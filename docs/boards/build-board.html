llm-proxy build board — proxy for LLM inference

Now — v0.2.0 "production-ready serving": stop claiming "performant" without evidence, and be safe to run unattended. v0.1.0 "LLM gateway" shipped 2026-08-08 and is tagged. v0.0.1 shipped 2026-08-01: the live smoke test ran against the real OpenAI and Anthropic endpoints and passed all four cases (both providers, streaming and not) on the first attempt. v0.1.0's SHIP GATE — per-request token counts (input / cache-read / cache-write / output) and TTFT/TPOT reach the access log for live traffic; a token-based rate limit is enforced; and the proxy fails over from one provider to another mid-request without the client seeing an error. All three clauses verified end to end, against mock upstreams — not against real providers. Token counts + TTFT/TPOT: QA-1 and QA-10, against a mock with known pacing (observed ttft=402ms/tpot=122.129ms/max_stall=152ms in the actual access log). Provider failover (WP-35): testing/diffrig/tests/failover_e2e.rs drives the real binary against a real dialect config and a mock forced to 429 — exact attempt accounting, the credential-isolation negative (standby's key only), and the standby's own Host header, all mutation-tested. Token-based rate limiting: testing/diffrig/tests/auth_e2e.rs, verified last — it could not be verified honestly until WP-50 increment 2a gave the limiter a proxy-assigned identity to key on, since before that a caller could reset its own quota by changing its own Authorization header. Unlike v0.0.1, this release was tagged without running its live-provider drill — it exists (testing/diffrig/tests/live_gate_v0_1_0.rs, one command, three billable calls) and was deliberately not run before tagging; recorded in docs/MILESTONES.md as a named departure, not a gap that was missed. WP-35's scope closed narrower than its title: same-dialect fallback only — cross-dialect (openai → anthropic) is a deliberate hard error, split into new WP-52 (v1.0.0) rather than left as a silent gap. v0.2.0's SHIP GATE — a published capacity report (p99, tokens/sec ceiling, RSS under sustained long-lived streams) from a run that is not harness-bound, plus /config_dump and /stats on the admin endpoint, plus a config swap under live traffic with zero dropped streams. Two of the three clauses CLOSED 2026-08-09; the capacity report is now the only one open, and it has a named blocker. /config_dump and /stats — closed: /config_dump's redaction is structural (WP-50 increment 1), and /stats now reports real traffic, not merely a correctly-rendered empty registry — WP-23 increments 4/5/6a landed the Prometheus renderer, a registry that survives a config swap, and cluster stat call sites, proven end to end by crates/proxy/tests/stats_e2e.rs and mutation-verified. Increment 6b (listener stats, LLM-token stats) remains open but doesn't reopen this clause, which was written against cluster traffic. Config swap under live traffic — closed: SIGHUP now triggers a real reload (a bad config keeps the old snapshot and logs, never taking the proxy down), and testing/diffrig/tests/swap_under_load.rs proves zero dropped streams under 6 concurrent SSE/non-streaming requests during the swap, asserting the SSE terminal frame rather than a request count (this proxy never injects into a truncated stream, so a count-based check would miss a silent truncation). A defect then surfaced IN the already-closed /config_dump clause and is worth naming plainly: found 2026-08-09 by writing user documentation against the code, not by a test — the admin server's own config handle was never enrolled where a SIGHUP reload actually publishes, so /config_dump//clusters kept serving the BOOT snapshot forever, including after a real reload. Fixed structurally (a registry that enrolls a handle the same step it hands one out) and verified end to end: real binary, real SIGHUP, HTTP response bytes asserted to change; a follow-up made the original mistake not just discouraged but uncompilable. The capacity report is the one open clause, and its blocker is now cleared — but the report itself still does not exist. Found 2026-08-09 while building the swap test: loadgen::driver::execute could not detect SSE stream truncation — it classified a streaming request as successful once the body ended without a transport error, never checking for the terminal frame, so a run in which the proxy truncated every stream would have reported a 0% error rate. Fixed and merged the same day, on main, inside this board's 1146 — and a second, larger defect found alongside it: every failed request's time-to-failure was feeding the latency percentiles, so a proxy collapsing under load would have measured as getting faster. Both mutation-verified; percentiles now cover successful requests only. What remains is unglamorous: no sweep has actually been run against the fixed instrument, so zero p99/tokens-per-sec/RSS numbers are published. The Linux /proc sampler is unverified but is no longer a blocker (owner decision 2026-08-09) — the gate asks for a run that isn't harness-bound, not specifically Linux, and the macOS sampler path is the verified one; what IS still open on that clause is WP-15 h1 connection reuse (h2 got a per-worker multiplexed cache today; h1 still burns two ephemeral ports per request and caps the rig near ~8k streams). Since then (2026-08-20/21): the sweep's prerequisites, which had not existed, now do. There was no standalone LLM upstream anywhere in the tree — only in-process test fixtures a diffrig test spawns and drops — so testing/mockupstream (a real long-lived binary) and scripts/capacity-sweep.sh (make sweep, make sweep-compare) were built to drive it. Separately, the configuration format itself could not produce an HTTP/2 upstream at all — lower.rs never emitted typed_extension_protocol_options, so every provider cluster the format we tell users to write actually built was HTTP/1.1, connect-per-request; now opt-in per provider via protocol: http2, default unchanged. The first sweep run was entirely a harness artifact — a zero-latency mock drove ~5,800 connects/sec at concurrency one against a box sustaining ~546/sec, exhausting ephemeral ports before the proxy was ever tested; fixed by making the mock LLM-shaped and deriving the SLO from generation time. The FIRST real ceiling found is 202 concurrent streams — hyper's h2 server defaults max_concurrent_streams to 200, confirmed in the dependency source in use, and the proxy multiplexes onto one upstream connection without opening a second. This is a known implementation gap, not a capacity number, and it does not close this clause — no p99/tokens-per-sec/RSS report exists yet. An h1-vs-h2 comparison sweep was in flight as this board was refreshed; its numbers are not available and are not guessed at here. The honest read on v0.1.0: all three gate clauses are proven against mocks that were built to exercise exactly these failure paths (a forced 429, an exhausted budget) — arguably a better instrument than an on-demand real-provider drill for those two, but that is an argument, not the v0.0.1 standard, which was a manual run against real endpoints, executed and recorded. Second standing risk, unchanged since 2026-08-01: the LLM layer stacks on serving foundations that are not finished — no connection pooling (WP-15, still connect-per-stream), no downstream h2 (WP-10), watermarks aliased to buffering rather than real backpressure (WP-11) — none exercised by the tests that closed v0.1.0's gate. WP-41, the black-box QA suite, found five real bugs across the two milestones — no dialect access logs at all, %REQ(:METHOD)% always - (Envoy mode too), no response flag on a mid-stream failure, a JSON-float usage report silently billed as zero (WP-48), and %LLM_RESPONSE_CHUNKS% over-counting by one on every response with a body. All five fixed; one had been described as intended in its own doc comment — the class of defect an inside view cannot see. WP-50 increment 2a (downstream authentication, 2026-08-08) was not planned v0.1.0 scope — it became the precondition once the rate-limit clause turned out to be advisory by construction. Proxy-issued virtual keys, keyed HMAC-SHA-256 verified in constant time, fail closed, an Authenticator trait chain so OIDC lands later without reshaping anything above it. Increments 2b (persistent key store), 2c (OIDC), and 3 (tenants/budgets/admin CRUD) remain, as does WP-47's migration of the three pre-existing borrowed-message filters — only increment 1, the vendored auth.proto itself, landed alongside 2a.
