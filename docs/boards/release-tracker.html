How a ticket earns its slot

Answer in order. The first question that discriminates wins.

  1. Does it block the current ship gate? Then it is the work. Nothing below matters.
  2. Is it a correctness or security defect on a path we already serve? Ship gates don't protect broken behavior that's already live. The missing-credentials P0, the access-log credential leak, and all four QA-suite findings came in this way — the last of which is why the suite outranks feature work when it reports.
  3. Does it violate a ground rule? A silently ignored config field is a P0 by definition. Usually small, always ahead of feature work in the same milestone.
  4. Otherwise, priority order within the current milestone. P0, then P1, then P2.
  5. Milestone empty? Pull from the next one. Don't pull P2 breadth work forward because it's easy — that's how the LLM layer stayed at "two files" as long as it did.

A ticket that fits no milestone doesn't get worked. It gets a P3 and a line in the plan. The backlog is allowed to be large; the active set has to be small and named.

P2 is a commitment, not a graveyard. The 2026-07-26 pivot moved LLM work ahead of parity work in time. It cancelled nothing — xDS, the admin server, the corpus scorecard, ext_authz/ext_proc, and downstream h2 all remain owed, and v1.0.0 depends on them.
